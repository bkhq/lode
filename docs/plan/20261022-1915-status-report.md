## Context

- `lode-core::http` already has ureq + rustls, `${ENV}` header expansion,
  `scheme_allowed` and same-host credential scoping.
- `state.json` holds most of what is reported; the supervisor loop
  (`lode-supervisor/src/supervise.rs`) knows status transitions, restarts and
  update/rollback outcomes.
- OTLP/HTTP JSON is the standard push protocol accepted by the OTel Collector and
  most observability backends; no OpenTelemetry crate is needed (they pull in
  tokio/protobuf) — the JSON body is built with serde_json.

## Proposal

### 1. Config

```toml
[report]
endpoint    = "https://otel.example.com"   # any OTLP/HTTP base: POSTs {endpoint}/v1/metrics, /v1/logs
                                           # lode-server: "https://lode.bk.io/r/otlp" (self-hosted: its own origin)
interval    = 300                          # seconds between metric exports; default 300
headers     = ["Authorization: Bearer ${OTEL_TOKEN}"]
attributes  = { "deployment.environment.name" = "prod", region = "hk" }
instance_id = "web-01"                     # default: host name
```

- Off unless `endpoint` is set. One shape for every backend: lode has no
  lode-server special case; a lode-server is just an `endpoint` with a `pat_…`
  bearer in `headers`, and the server resolves the package from `service.name`
  (and `service.namespace` or the token owner).
- Standard env fallbacks: `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_HEADERS`,
  `OTEL_RESOURCE_ATTRIBUTES` (merged under `attributes`); lode's own
  `--report-endpoint` / `LODE_REPORT_ENDPOINT`, `LODE_REPORT_INTERVAL`.
- `[report].headers` go to `endpoint` only; `[http].headers` are never sent
  there.
- `endpoint` HTTPS-only unless `[http].allow_insecure`; `[report]` targets and
  headers are pinned across config reloads (like `[trust]`).

### 2. Payload (OTLP JSON)

Resource attributes: `service.name` (= `[global].app`), `service.version` (current), `service.instance.id`,
`host.name`, `host.arch`, `os.type`, `process.pid` (lode), `lode.version`,
`lode.channel`, `lode.report.interval`, plus `attributes`.

Metrics (gauges, every `interval`): `lode.app.up` (0/1), `lode.app.status`
(1, attribute `status`), `lode.app.restarts`, `lode.app.uptime` (s),
`lode.update.available` (0/1, attribute `version`), `lode.app.last_good`
(1, attribute `version`), `lode.resource.version` (1 per resource, attributes
`resource`, `version`).

Logs (sent when they happen): `event.name` ∈ `lode.started`, `lode.stopping`,
`lode.updated` (from/to), `lode.rolled_back` (from/to, reason),
`lode.paused` (reason), `lode.resource.updated` (resource, from/to),
`lode.check.failed` (error).

### 3. Runtime

- A `lode-core::report` module builds the bodies; a reporter thread in the
  supervisor receives snapshots/events over a channel and POSTs them (10 s
  timeout, bounded queue of 100 events; oldest dropped), so a slow or down
  server never blocks supervision. Failures are logged with backoff; no disk
  queue, no replay. `429`/`503` honour `Retry-After`.
- Bare `lode` only; `lode-cli` never reports. Embedded `serve_core` hosts get it
  through the same config.

### 4. Tests

- Unit: config parse/validation (endpoint scheme, header expansion, pinned on
  reload), payload golden JSON for metrics and logs, env fallbacks.
- Supervisor: events emitted on start/update/rollback/pause with a stub endpoint.
- e2e: a Bun OTLP stub receives `started` + metrics with `service.name` /
  `service.version`, then `lode.updated` after an update.

architecture (+zh), integration/operations (+zh), `lode.example.toml`, README,

## Risks

- Hostname and labels leave the machine — off by default, documented.
- Large fleets on lode-server: 300 s default keeps write load low.

## Scope

lode-core (config, report module), lode-supervisor (reporter thread, events),
lode CLI flags, docs, tests. No change to the state.json contract.

## Alternatives

- CloudEvents webhook: event envelope only, no metric semantics; reachable via a
  Collector if needed.
- Prometheus pull endpoint: needs a listener; possible later.
- `opentelemetry` crates: tokio/protobuf weight in a static single binary.

## Annotations

Decisions (2026-10-22): OTLP/HTTP JSON; default interval 300 s, configurable.
No `lode_server` switch: the same `endpoint` + `headers` configuration serves
lode-server (`<origin>/r/otlp`, self-hosted included) and any OTel backend;
lode-server resolves the package from `service.name` and `service.namespace`
or the token owner.

Implementation notes (2026-10-22):

- No `OTEL_EXPORTER_OTLP_*` / `OTEL_RESOURCE_ATTRIBUTES` fallbacks: containers
  often set them for the app, and lode would silently start reporting (with the
  app's collector credentials) under the app's `service.name`. Reporting stays
  off unless `[report].endpoint` / `--report-endpoint` / `LODE_REPORT_ENDPOINT`
  is set.
- The event queue drops new events when 100 are pending (a bounded
  `sync_channel`), rather than the oldest.
- Metrics are also exported at start and once more on shutdown, so a receiver
  sees `stopped` without waiting for the host to go silent.
- `[report]` is part of the reload pin check (`trust_anchor_changed`).
- Joint test against lode-server's `/r/otlp` (real routes, temp db): instance
  stored with version/status/os/arch, `lode.started` / `lode.stopping` events,
  final status `stopped`. lode-server now treats a `stopped` instance as offline.
